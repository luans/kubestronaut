# Day 5 - Supply Chain & Runtime Security

## Image Scanning: Trivy and Grype

### Why scan images?

Container images are built on layers of software. Every OS package and every dependency can contain known vulnerabilities (CVEs - Common Vulnerabilities and Exposures).

**The problem cycle:**
1. Base image `ubuntu:22.04` contains 150 packages
2. Each package can have CVEs discovered at any time
3. Your image inherits all those CVEs
4. Without scanning, you don't know what's running in production

### Trivy

Trivy is an open source vulnerability scanner from Aqua Security. It is the most popular and comprehensive scanner for the Kubernetes ecosystem.

**What Trivy scans:**
- OS packages (apk, apt, rpm)
- Language dependencies (pip, npm, cargo, go modules, maven)
- Configuration files (Kubernetes, Docker, Terraform)
- Secrets (tokens, keys, passwords) in code
- Software licenses (compliance)
- SBOMs (Software Bill of Materials)

**Installation:**
```bash
# macOS
brew install trivy

# Linux
wget https://github.com/aquasecurity/trivy/releases/download/v0.50.0/trivy_0.50.0_Linux-64bit.tar.gz
tar -xzf trivy_0.50.0_Linux-64bit.tar.gz
```

**Basic usage:**
```bash
# Scan an image
trivy image nginx:latest

# Scan only for CRITICAL and HIGH severity
trivy image --severity HIGH,CRITICAL nginx:latest

# Scan and exit with error if CRITICAL is found
trivy image --exit-code 1 --severity CRITICAL nginx:latest

# Scan local filesystem (e.g., code repository)
trivy fs .

# Scan Kubernetes manifests for misconfigurations
trivy k8s --report summary cluster

# Generate SBOM
trivy image --format spdx-json --output sbom.json nginx:latest

# Scan with JSON output for CI/CD
trivy image --format json --output result.json nginx:latest

# Ignore unfixed vulnerabilities
trivy image --ignore-unfixed nginx:latest
```

**Typical output:**
```
nginx:latest (debian 11.6)
Total: 142 (UNKNOWN: 0, LOW: 91, MEDIUM: 44, HIGH: 7, CRITICAL: 0)

┌────────────────┬───────────────┬──────────┬───────────────────┬──────────────────┐
│    Library     │ Vulnerability │ Severity │ Installed Version │  Fixed Version   │
├────────────────┼───────────────┼──────────┼───────────────────┼──────────────────┤
│ libssl1.1      │ CVE-2023-xxxx │ HIGH     │ 1.1.1n-0+deb11u4  │ 1.1.1n-0+deb11u5 │
└────────────────┴───────────────┴──────────┴───────────────────┴──────────────────┘
```

**CI/CD integration (GitHub Actions):**
```yaml
- name: Scan image with Trivy
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: 'my-app:${{ github.sha }}'
    format: 'sarif'
    output: 'trivy-results.sarif'
    severity: 'CRITICAL,HIGH'
    exit-code: '1'
```

### Grype

Grype is the vulnerability scanner from Anchore. It focuses on speed and accuracy.

**Differences between Trivy and Grype:**

| Aspect | Trivy | Grype |
|---|---|---|
| Scope | Broad (vulns + misconfigs + secrets) | Focused on vulnerabilities |
| Speed | Fast | Very fast |
| Databases | Multiple (NVD, Alpine, Debian...) | grypedb (consolidated) |
| SBOM | Generates and consumes | Primarily consumes |
| Misconfigs | Yes | No |
| Kubernetes scanning | Yes | Not directly |

**Basic Grype usage:**
```bash
# Installation
brew install grype

# Scan an image
grype nginx:latest

# Scan only HIGH and CRITICAL
grype nginx:latest --fail-on high

# Scan with SBOM generated by Syft
syft nginx:latest -o json | grype

# Scan local directory
grype dir:.

# JSON output
grype nginx:latest -o json > result.json
```

### Syft (SBOM generation)

Syft (also from Anchore) generates SBOMs that can be consumed by Grype:

```bash
# Generate SBOM in SPDX format
syft nginx:latest -o spdx-json > sbom.spdx.json

# Generate SBOM in CycloneDX format
syft nginx:latest -o cyclonedx-json > sbom.cdx.json

# Scan SBOM with Grype
grype sbom:sbom.spdx.json
```

### Scanning best practices

```bash
# 1. Use minimal base images
FROM gcr.io/distroless/static:nonroot  # No shell, no package manager
FROM alpine:3.19  # Minimal, fewer packages = fewer CVEs
FROM scratch  # No OS (only for static binaries)

# 2. Multi-stage builds
FROM golang:1.22 AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o app .

FROM gcr.io/distroless/static:nonroot  # Clean final image
COPY --from=builder /app/app /app
ENTRYPOINT ["/app"]

# 3. Scan at multiple points:
# - Build time (CI/CD)
# - Registry push (admission control)
# - Runtime (periodic in production)
```

## Image Signing: Cosign and Notary

### Why sign images?

Without signing, there is no guarantee that the image you are using is the same one that was published. Supply chain attacks can replace legitimate images with malicious ones.

**The secure flow:**
```
Build → Sign → Push → Verify → Deploy
         ↑              ↑
      (Cosign)     (Admission Controller
                    or Policy Engine)
```

### Cosign (Sigstore)

Cosign is the image signing tool from the Sigstore project. It is the most widely adopted standard in the Kubernetes/CNCF ecosystem.

**Installation:**
```bash
brew install cosign
```

**Generate a key pair:**
```bash
# File-based key (simplest)
cosign generate-key-pair

# Generates: cosign.key (private) and cosign.pub (public)
```

**Sign an image:**
```bash
# Sign and push the signature to the registry
cosign sign --key cosign.key my-registry.io/my-app:1.0.0

# The signature is stored in the registry as:
# my-registry.io/my-app:sha256-<digest>.sig
```

**Verify an image:**
```bash
# Verify with the public key
cosign verify --key cosign.pub my-registry.io/my-app:1.0.0

# JSON output for automation
cosign verify --key cosign.pub my-registry.io/my-app:1.0.0 | jq .
```

**Keyless signing (with Sigstore Fulcio + Rekor):**
```bash
# Sign without private keys (uses OIDC identity)
# Requires an environment with OIDC (GitHub Actions, Google Cloud, etc.)
cosign sign my-registry.io/my-app:1.0.0  # without --key

# Verify keyless
cosign verify \
  --certificate-identity=https://github.com/org/repo/.github/workflows/build.yml@refs/heads/main \
  --certificate-oidc-issuer=https://token.actions.githubusercontent.com \
  my-registry.io/my-app:1.0.0
```

**Transparency Log (Rekor):**
- All keyless signatures are recorded in Rekor (public, immutable log)
- Enables auditing of when and by whom an image was signed

**Attestations (SBOM and scan results):**
```bash
# Attach SBOM as an attestation
cosign attest --predicate sbom.spdx.json --type spdxjson \
  --key cosign.key my-registry.io/my-app:1.0.0

# Verify attestation
cosign verify-attestation --key cosign.pub \
  --type spdxjson my-registry.io/my-app:1.0.0
```

### Notary (Docker Content Trust)

Notary is the older image signing system, based on The Update Framework (TUF).

**Notary concepts:**
- **Notary Server**: stores trust metadata
- **Root key**: master key (offline, highly protected)
- **Targets key**: signs content
- **Timestamp key**: ensures freshness
- **Snapshot key**: ensures consistency

**Docker Content Trust (DCT) uses Notary:**
```bash
# Enable Docker Content Trust
export DOCKER_CONTENT_TRUST=1

# Push with automatic signing
docker push my-registry.io/my-app:1.0.0

# Pull automatically verifies signature
docker pull my-registry.io/my-app:1.0.0
```

### Cosign vs Notary

| Aspect | Cosign/Sigstore | Notary v2 |
|---|---|---|
| Standard | Emerging, CNCF | OCI spec |
| Keyless | Yes (via OIDC) | No |
| Complexity | Low | High |
| Public log | Rekor | No (private) |
| Adoption | High (Kubernetes, Tekton) | High (Docker, Harbor) |

## Admission Controllers: OPA/Gatekeeper and Kyverno

### What are Admission Controllers

Admission Controllers are plugins that intercept requests to the Kubernetes API after authentication/authorization, and can **validate** (reject) or **mutate** (modify) resources.

```
Authentication → Authorization → Mutating Admission → Validating Admission → etcd
```

**Types:**
- **MutatingAdmissionWebhook**: can modify the resource (e.g., inject a sidecar)
- **ValidatingAdmissionWebhook**: only validates, does not modify (e.g., reject root containers)

### OPA (Open Policy Agent) / Gatekeeper

OPA is a general-purpose policy engine. Gatekeeper is the OPA integration for Kubernetes.

**Gatekeeper architecture:**
```
kubectl apply → kube-apiserver → Gatekeeper Webhook → OPA → Rego policy
                                        ↓
                                   Allow/Reject
```

**Installation:**
```bash
kubectl apply -f https://raw.githubusercontent.com/open-policy-agent/gatekeeper/master/deploy/gatekeeper.yaml
```

**Gatekeeper components:**

1. **ConstraintTemplate**: defines the policy in Rego
2. **Constraint**: an instance of the policy with parameters

```yaml
# ConstraintTemplate: define the policy
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8srequiredlabels
spec:
  crd:
    spec:
      names:
        kind: K8sRequiredLabels
      validation:
        openAPIV3Schema:
          properties:
            labels:
              type: array
              items:
                type: string
  targets:
  - target: admission.k8s.gatekeeper.sh
    rego: |
      package k8srequiredlabels

      violation[{"msg": msg}] {
        provided := {label | input.review.object.metadata.labels[label]}
        required := {label | label := input.parameters.labels[_]}
        missing := required - provided
        count(missing) > 0
        msg := sprintf("Missing required labels: %v", [missing])
      }

---
# Constraint: apply the policy
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sRequiredLabels
metadata:
  name: require-app-label
spec:
  match:
    kinds:
    - apiGroups: [""]
      kinds: ["Pod"]
    namespaces:
    - production
  parameters:
    labels:
    - "app"
    - "version"
```

**Rego: OPA's policy language**
```rego
# Deny privileged containers
package kubernetes.admission

deny[msg] {
  input.request.kind.kind == "Pod"
  container := input.request.object.spec.containers[_]
  container.securityContext.privileged == true
  msg := sprintf("Container '%v' cannot be privileged", [container.name])
}
```

### Kyverno

Kyverno is a Kubernetes-native policy engine - policies are written in YAML, not Rego.

**Kyverno advantages:**
- Native YAML (no separate policy language)
- Can generate resources (e.g., automatically create NetworkPolicy)
- Can mutate resources (e.g., add labels)
- Easier for teams already familiar with Kubernetes

**Types of Kyverno policies:**

```yaml
# ClusterPolicy for validation
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-privileged-containers
spec:
  validationFailureAction: Enforce  # Enforce = blocks; Audit = only logs
  rules:
  - name: check-privileged
    match:
      any:
      - resources:
          kinds: ["Pod"]
    validate:
      message: "Privileged containers are not allowed"
      pattern:
        spec:
          containers:
          - =(securityContext):
              =(privileged): "false"

---
# Mutation: automatically add a label
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: add-default-labels
spec:
  rules:
  - name: add-labels
    match:
      any:
      - resources:
          kinds: ["Pod"]
    mutate:
      patchStrategicMerge:
        metadata:
          labels:
            managed-by: kyverno

---
# Generation: create a NetworkPolicy for each namespace
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: add-networkpolicy
spec:
  rules:
  - name: default-deny
    match:
      any:
      - resources:
          kinds: ["Namespace"]
    generate:
      kind: NetworkPolicy
      name: default-deny-all
      namespace: "{{request.object.metadata.name}}"
      data:
        spec:
          podSelector: {}
          policyTypes:
          - Ingress
          - Egress
```

### OPA/Gatekeeper vs Kyverno

| Aspect | OPA/Gatekeeper | Kyverno |
|---|---|---|
| Language | Rego (custom) | Native YAML |
| Learning curve | High | Low |
| Flexibility | Very high | High |
| Resource generation | No (pure OPA) | Yes |
| Mutation | Via separate webhook | Native |
| Use outside K8s | Yes (OPA is general-purpose) | No |
| CNCF | Graduated | Incubating |

## Falco: Runtime Threat Detection

### What is Falco

Falco is a CNCF runtime security tool that detects anomalous behavior in containers and the Linux kernel using eBPF or a kernel module.

**What Falco monitors:**
- Syscalls (system calls)
- Process behavior
- Access to sensitive files
- Network connections
- Container activity

### How Falco works

```
Application in Container
        │
        │ syscalls
        ▼
┌──────────────────┐
│  Linux Kernel    │
│  ┌────────────┐  │
│  │  eBPF/     │  │
│  │  Kernel    │  │
│  │  Module    │  │
│  └─────┬──────┘  │
└────────┼─────────┘
         │ events
         ▼
┌─────────────────┐
│  Falco Engine   │
│  (Rules Engine) │
└────────┬────────┘
         │ alerts
         ▼
┌──────────────────┐
│  Outputs:        │
│  - syslog        │
│  - stdout        │
│  - file          │
│  - gRPC          │
│  - webhook       │
└──────────────────┘
```

### Installing Falco

```bash
# Helm chart
helm repo add falcosecurity https://falcosecurity.github.io/charts
helm install falco falcosecurity/falco \
  --set driver.kind=ebpf \
  --namespace falco \
  --create-namespace
```

### Falco rules

```yaml
# /etc/falco/falco_rules.yaml

# Detect a shell in a container
- rule: Terminal shell in container
  desc: A shell process was started in a container
  condition: >
    spawned_process and container and
    shell_procs and proc.tty != 0 and
    container_entrypoint
  output: >
    A shell was opened in a container
    (user=%user.name user_loginuid=%user.loginuid %container.info
    shell=%proc.name parent=%proc.pname cmdline=%proc.cmdline
    pid=%proc.pid terminal=%proc.tty container_id=%container.id
    image=%container.image.repository)
  priority: NOTICE
  tags: [container, shell, mitre_execution]

# Detect writes to /etc
- rule: Write below etc
  desc: Detect writes to /etc inside containers
  condition: >
    write_and_not_read and
    container and
    (fd.name startswith /etc)
  output: >
    File below /etc opened for writing
    (user=%user.name command=%proc.cmdline parent=%proc.pname
    file=%fd.name program=%proc.name gparent=%proc.aname[2]
    container_id=%container.id image=%container.image.repository)
  priority: ERROR

# Detect access to the Docker socket
- rule: Contact Docker Socket
  desc: Detect access to the Docker socket (possible container escape)
  condition: >
    open_write and
    fd.name = /var/run/docker.sock
  output: >
    Docker socket access detected
    (user=%user.name command=%proc.cmdline container_id=%container.id)
  priority: CRITICAL
```

### Falco rule priorities

From most to least severe:
1. `EMERGENCY`
2. `ALERT`
3. `CRITICAL`
4. `ERROR`
5. `WARNING`
6. `NOTICE`
7. `INFORMATIONAL`
8. `DEBUG`

### Useful macros and lists

```yaml
# Macros
- macro: container
  condition: container.id != host

- macro: spawned_process
  condition: evt.type = execve and evt.dir = <

- macro: shell_procs
  condition: proc.name in (shell_binaries)

# Lists
- list: shell_binaries
  items: [bash, csh, ksh, sh, tcsh, zsh, dash]

- list: sensitive_files
  items: [/etc/shadow, /etc/sudoers, /etc/pam.conf]
```

### Falco Sidekick

Falcosidekick forwards Falco alerts to multiple destinations:

```yaml
outputs:

    routingKey: <routing_key>

```

## Supply Chain Security Concepts (SLSA)

### SLSA (Supply-chain Levels for Software Artifacts)

Framework for measuring software supply chain security:

| Level | Requirement |
|---|---|
| SLSA 1 | Scripted build (not manual), provenance available |
| SLSA 2 | Build in a controlled service, provenance signed |
| SLSA 3 | Isolated build, auditable provenance |
| SLSA 4 | Hermetic and reproducible build |

### Secure pipeline: from code to cluster

```
Code → CI/CD → Build → Scan → Sign → Push Registry → Verify → Deploy
  ↑       ↑      ↑       ↑       ↑          ↑             ↑
 SAST  Secrets  SBOM   Trivy  Cosign    Admission     Runtime
 SCA    scan          /Grype          Controller     (Falco)
```

## Key Takeaways for the KCSA Exam

- Trivy: broad scanner (vulns + misconfigs + secrets + K8s)
- Grype: focused on vulnerabilities, faster
- Syft: SBOM generation, complements Grype
- Cosign signs images and stores the signature in the registry (as an OCI artifact)
- Keyless signing uses OIDC + Rekor (public, immutable log)
- Admission Controllers: Mutating (modifies) → Validating (validates) → etcd
- Gatekeeper = OPA + Kubernetes integration; policies in Rego
- Kyverno: native YAML policies; can validate, mutate, and generate resources
- `validationFailureAction: Enforce` blocks; `Audit` only logs
- Falco monitors syscalls via eBPF or kernel module
- Falco detects: shells in containers, access to sensitive files, container escape
- SLSA defines maturity levels for supply chain security
- Distroless images: no shell, no package manager, minimal surface
- Multi-stage builds: the final image does not contain build tools
